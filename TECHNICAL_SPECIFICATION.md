# Техническое задание: мультиагентная система для разработки ПО

Версия 0.1

## 1. Назначение и ожидаемый результат

Разработать собственную систему LLM-агентов, которая получает задачу изменения
программного проекта, составляет план, выполняет изменения, запускает проверки,
независимо оценивает результат и выдаёт пользователю проверяемый набор изменений.
Агенты работают в едином процессе с общей моделью состояния и передачей результатов.
Система должна поддерживать ограниченную автономность и воспроизводимые эксперименты.

Особый приоритет — изоляция агентов и исполняемого ими кода в sandbox-средах.
Изоляция должна быть реализована технически, измерена и проверена негативными
сценариями. Инструкции модели сами по себе не являются механизмом ограничения доступа.

Результат работы над задачей: patch или коммиты в отдельной ветке, отчёт о выполнении,
протокол проверок, решение валидатора, журнал действий и сведения об использованных
моделях и ресурсах. Успешность системы нельзя подтверждать только ответом LLM.

## 2. Границы проекта и условия эксплуатации

### 2.1. Согласованные положения

- Отдельный проект `multi-agent-system`; исходный код приложения — в `src/`.
- Kaibain — отдельная визуализация задач. Агентная логика, память, sandbox-управление
  и наблюдаемость разрабатываются в этом проекте.
- Создаются собственные агенты на основе LLM и выбранного агентного фреймворка.
  OpenCode, Claude Code и Codex могут использоваться как внешние ориентиры для
  сравнения; готовый coding agent не заменяет основной реализуемый агентный цикл.
- Основной узел: MacBook Air M4, 16 ГБ RAM. На нём размещаются управление системой,
  агентные среды, рабочие копии проектов и локальные данные.
- Узел инференса: PC с Windows 10, Ryzen 7500F, RX 7700 XT, 12 ГБ VRAM, 32 ГБ RAM.
  Он предоставляет API моделей по сети. Версии ОС, драйверов и поддерживаемый backend
  необходимо проверить перед выбором движка.
- Приоритет платформ: macOS, затем Windows. Обязательный Windows-сценарий первой
  версии — сервер моделей; перенос всего управляющего узла на Windows — расширение.
- Локальные модели исследуются обязательно. Внешние, в том числе бесплатные, API
  допускаются как дополнительный режим и источник сравнительных результатов.

### 2.2. Предлагаемый объём первой версии

Поддержать один пользовательский проект за запуск и небольшие задачи разработки:
исправление дефекта, добавление функции, рефакторинг с сохранением поведения,
добавление тестов и обновление документации. Базовый демонстрационный стек — Python
с автоматически запускаемыми тестами; другие языки добавляются через профили среды.

Репозиторий должен иметь зафиксированный исходный commit и воспроизводимую команду
проверки. Первичная приёмка проводится на специально подготовленных репозиториях.
Поддержка произвольного проекта без описания зависимостей и проверок не гарантируется.

По умолчанию задача разрешает локальное создание рабочей среды, изменение файлов
в ней и выполнение разрешённых проверок в пределах заданных бюджетов. Слияние в
основную ветку, push, публикация, доступ к дополнительным каталогам, расширение сети
и расходы на платные API требуют отдельного разрешения пользователя. Эти границы
автономности — предлагаемая политика первой версии.

Облачное развёртывание управляющей системы, многопользовательские роли, Kubernetes
кластер, обучение фундаментальной LLM и автоматическое развёртывание в production
не входят в первую версию. Они могут рассматриваться в сравнении альтернатив.

Внутренние состояния запуска должны как минимум различать очередь, планирование,

паузу, готовность к приёмке, ошибку и отмену. Подзадачи имеют собственные состояния.
Отмена и ошибка не должны отображаться как успешно завершённая задача.

## 4. Агенты, взаимодействие и проверка решений

| ID | Требование |
| --- | --- |
| A-01 | Координатор декомпозирует задачу, определяет зависимости, использует результаты исполнителей и формирует итог. Планирование LLM отделено от детерминированного планировщика запусков и правил допуска. |
| A-02 | Разработчик исследует рабочую копию, изменяет код, запускает разрешённые инструменты и передаёт изменения с доказательствами выполнения. |
| A-03 | Валидатор использует LLM другого семейства, чем проверяемый разработчик. Проверять семейство по метаданным маршрута; при отсутствии подходящей модели ожидать ресурс, не подменять независимую проверку самооценкой. |
| A-04 | Валидатор получает постановку, критерии, исходный commit, diff и результаты инструментов. Проводит повторные проверки в чистой среде. Вердикт содержит проверенные критерии, замечания, свидетельства и решение о доработке/приёмке. |
| A-05 | Для каждой роли создать собственный системный промпт, перечень инструментов, схемы входа/выхода, правила остановки и границы доступа. Версии сохранять с запуском. |
| A-06 | Создать собственные файлы скиллов как минимум для анализа репозитория, реализации изменения, запуска тестов и проверки результата. Создать содержательные Markdown-инструкции о роли, правилах, проектном контексте и работе с памятью. Они должны реально загружаться и отражаться в трассировке. |
| A-07 | Все передачи работы идут через структурированные сообщения с task_id, run_id, attempt_id, ролью и ссылками на артефакты. Запретить произвольное изменение агентом состояния чужой задачи. |
| A-08 | Схемы вызовов, права, бюджеты, версии и переходы состояний проверяет код. LLM не может разрешать себе новые полномочия. |

Роли могут работать последовательно; одновременный инференс не обязателен для
мультиагентности. Обязательны единый процесс, специализация, передача результатов,
обратная связь и разные модельные маршруты. Число одновременно активных сред
настраивается с учётом ресурсов Mac.

## 6. Sandbox-изоляция — обязательная подсистема

### 6.1. Модель угроз и доверенные границы

Защищаемые ресурсы: файлы и секреты пользователя, основной репозиторий, управляющая
БД, память других задач, модельные ключи, sandbox runtime, сеть и ресурсы хоста.

Недоверенные входы: текст задачи, содержимое репозитория и документации, вывод
инструментов, зависимости, предложенные LLM команды и созданный код. Рассмотреть
ошибки агента, prompt injection, вредоносные install/build/test-скрипты, попытки
выхода через файловые пути, утечки по сети и истощения ресурсов.

Доверенная часть включает управляющий сервис, проверку политик, брокер модельных
запросов/секретов и Sandbox Manager. Агентные workers и выполняемый код находятся
в управляемых изолированных средах. Проверка артефактов на хосте не должна исполнять
код из проекта. Границы процессов, ОС и виртуализации показать на диаграммах.

Абсолютная защита от неизвестных уязвимостей ядра/гипервизора не заявляется.
Для выбранного механизма описать остаточные риски и степень общей зависимости
между средами. Общий контейнерный runtime не следует выдавать за отдельную VM
на каждого агента без фактической проверки архитектуры.

### 6.2. Выбор механизма

**S-01.** Сравнить классы решений: обычные и усиленные контейнеры, runtime/sandbox,
полные VM, MicroVM. Рассмотреть инструменты из задания: Docker Sandboxes, E2B,
OpenSandbox, Microsandbox, gVisor, Kata Containers, Firecracker, K8s Agent Sandbox,
kagent, Google AX и agent-substrate. Классифицировать их по назначению; составить
краткую матрицу всех кандидатов и подробное сравнение минимум трёх подходящих.

Критерии: поддержка Apple Silicon и выбранной ОС, граница изоляции, запуск собственного
worker, управление через API/CLI, файловые и сетевые политики, лимиты, отмена,
очистка, наблюдаемость, автономная локальная работа, лицензия, расходы, RAM и время
старта. Не требуется устанавливать все варианты. Для основного кандидата выполнить
прототип с реальными проверками на Mac; для отклонённых сохранить причины.

**S-02.** Реализовать Sandbox Manager с операциями создания, подготовки, исполнения,
проверки состояния, экспорта артефактов, остановки и удаления. Каждый sandbox связан
с run_id/attempt_id и неизменяемым снимком политики. Использовать явно выбранный
backend; при недоступности изоляции блокировать выполнение, не переходить на shell хоста.

### 6.3. Файловая система, процессы и секреты

| ID | Требование |
| --- | --- |
| S-03 | Каждая попытка разработки получает отдельную рабочую копию; проверка результата — отдельную чистую среду. Межзадачный доступ запрещён. Git worktree допустим для организации изменений, но не заменяет sandbox. |
| S-04 | Предоставлять только явно подготовленный снимок проекта. Исключать секреты и локальные конфиги по профилю импорта, не полагаться только на .gitignore. Не монтировать домашний каталог, общий .git, SSH-agent, runtime sockets и управляющую БД. |
| S-05 | Запретить privileged-режим, доступ к устройствам и управляющему API runtime из среды агента. Использовать минимальные привилегии и возможности выбранного backend. Агент не изменяет собственную политику. |
| S-06 | Проверять пути при чтении, записи и экспорте, включая абсолютные пути, ../, symlink и архивные пути. Не допускать записи за пределы выделенной области. |
| S-07 | Провайдерские ключи хранить у доверенного брокера. Worker получает ограниченный идентификатор сессии, действующий только для разрешённых моделей, задач и бюджета; после завершения он отзывается. Секреты не попадают в промпты, файлы, логи и артефакты. |
| S-08 | Разрешённые инструменты запускаются внутри sandbox. Их входы и результаты ограничены схемой и размером. Административное управление sandbox остаётся у доверенного сервиса. |

### 6.4. Сеть и зависимости

**S-09.** По умолчанию запретить произвольный сетевой выход. Разрешить только
необходимые сервисы через проверяемые правила. Ограничить доступ к хосту, LAN,
служебным адресам и другим sandbox; исключение — явно выделенный endpoint брокера.
Учесть DNS, IPv4/IPv6, прямые IP, перенаправления и альтернативные протоколы.
Ограничение должно применяться ниже уровня промпта и инструментального API.

**S-10.** Разделить подготовку зависимостей и исполнение задачи. Зависимости
фиксируются lock-файлами/версиями, загружаются из разрешённых источников; install-
скрипты также исполняются в изоляции. После подготовки сокращать сетевые разрешения.
Общий кеш не должен позволять агенту подменять зависимости для других задач.
Предпочитать кеш только для чтения и отдельный writable-слой задачи.

**S-11.** Изменение сетевой политики требует отдельного решения пользователя и
создаёт событие аудита. Результат Jev/LLM не может самостоятельно расширить доступ.
Даже разрешённый endpoint может быть каналом передачи данных; этот остаточный риск
учитывается при выборе allowlist и профиля работы с внешними моделями.

### 6.5. Ресурсы и жизненный цикл

**S-12.** Ограничивать CPU, RAM, число процессов, рабочий диск, объём вывода команд,
время действия и всей задачи. Для модельных запросов отдельно ограничивать контекст,
выходные токены, число запросов и денежный бюджет. Лимиты проверяются принудительно.

Предлагаемый стартовый профиль для испытаний на Mac 16 ГБ:

| Параметр | Начальное значение, подлежит замеру |
| --- | --- |
| Активные тяжёлые sandbox | 1; разработка и валидация последовательно |
| Предел RAM рабочего sandbox | 4 ГБ |
| Суммарный бюджет sandbox-подсистемы с VM/runtime | 6 ГБ |
| CPU / процессы / рабочий диск | 2 vCPU / 128 процессов / 5 ГБ |
| Одна команда / одна задача | 120 секунд / 30 минут |
| Инструментальные действия / циклы исправления | 50 / 3 |
| Сохраняемый вывод одной команды | 1 МиБ; превышение явно отмечается |
| Запросы инференса на PC одновременно | 1 |

Это целевые настройки проекта, а не утверждение о достаточности ресурсов. После

## 7. Инструменты и интеграции

**T-01.** Реализовать инструменты чтения/поиска файлов, применения изменений,
просмотра diff, запуска разрешённых команд и тестов, чтения результатов проверок,
работы с памятью и передачи результата. Для каждого задать схему, права, таймаут,
лимит результата и структурированную ошибку.

**T-02.** Все инструменты должны проходить через единый контроль доступа и аудит.
Вывод команды считается недоверенными данными. Вызов инструмента из вывода другого
инструмента не исполняется автоматически.

**T-03.** Предоставить CLI или локальный API для запуска/наблюдения/отмены задач без
Kaibain. Интерфейс должен возвращать идентификатор запуска и структурированные ошибки.

**T-04.** Реализовать адаптер Kaibain через его публичный MCP/API: читать выбранную
задачу, публиковать подзадачи, статусы и ссылки/сводки результатов в доступных полях.
Не обращаться к SQLite Kaibain напрямую. Хранить соответствия идентификаторов,
применять expected_version, предотвращать повторную публикацию и циклы синхронизации.
Система владеет состоянием запуска; Kaibain отображает его проекцию. Действия
пользователя передаются как явные команды, а не как неявное разрешение на запуск.

**T-05.** Отказ визуализации не должен терять выполненную работу. Сохранять исходящие
события для последующей синхронизации. Четыре колонки Kaibain — укрупнённое отображение:
планирование → «Запланировано», выполнение/проверка → «В работе», результат для
пользователя → «Ревью», принятый пользователем результат → «Готово». Причины ожидания
и ошибки доступны отдельно; внутренние состояния не сводятся к четырём колонкам.

## 8. Память и актуальность данных

**M-01.** Реализовать три различимых уровня памяти:

1. Рабочий контекст шага/сессии: текущие наблюдения, сообщения и результаты инструментов.
2. Память запуска: план, подзадачи, checkpoints, решения, попытки и ссылки на артефакты.
3. Долговременная память проекта: подтверждённые соглашения, факты о проекте,
   принятые решения и полезные результаты завершённых задач.

**M-02.** Для записей хранить источник, область проекта, время, связанный commit,
автора/роль и статус проверки. Изменение файлов/commit инвалидирует зависимые факты.
Противоречивые сведения не перезаписываются молча; старые записи помечаются устаревшими.
Предположения агента не становятся подтверждёнными фактами без свидетельств.

**M-03.** Разделить историю событий и извлекаемые знания. Поддержать просмотр, исправление,
удаление и переиндексацию памяти, лимиты контекста и проверяемое суммирование.
Исключить перенос секретов и данных между проектами без разрешения.

**M-04.** Сравнить минимум три подхода/средства из задания: например, состояние workflow
и структурированное хранилище, гибридный retrieval, графовая/темпоральная память,
системы управления памятью. Кандидаты: Graphiti, Cognee, Letta, LangMem, Mem0,
LlamaIndex, PageIndex и другие из исходного списка. Зафиксировать достоинства,
недостатки, стоимость ресурсов и причины отказа. Объяснить, почему обычного RAG
недостаточно для состояния выполнения, версий, зависимостей и актуальности знаний
именно в этом проекте; проверить пользу выбранного дополнения экспериментом.

## 12. Нефункциональные требования и запуск

- **N-01:** основной профиль на Mac M4 16 ГБ должен проходить демонстрацию без
  исчерпания памяти; бюджет сервисов и sandbox подтверждается измерением.
- **N-02:** состояния, артефакты и память сохраняются между перезапусками;
  предоставить резервное копирование и проверенную процедуру восстановления.
- **N-03:** управляющие endpoints доступны локально. Межмашинный канал инференса
  ограничен нужными узлами и защищён аутентификацией и шифрованием либо туннелем.
- **N-04:** конфигурация, политики, роли и зависимости версионируются; секреты,
  веса моделей и рабочие данные не попадают в Git.
- **N-05:** предоставить диагностируемые команды настройки, запуска, проверки
  готовности и остановки. Агент-разработчик должен иметь возможность запустить

- **N-06:** ошибки должны содержать код, причину и доступное дальнейшее действие;

- **N-07:** при сбое sandbox backend и нарушении политики не ослаблять ограничения.
  При ошибках разрешённых действий сохранять частичные результаты и возможность диагностики.

## 13. Приёмочные сценарии

Все проверки выполняются на тестовых репозиториях и синтетических секретах.
Проверки лимитов используют малые безопасные бюджеты, а не неограниченную нагрузку.

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |

| AC-10 | Превышение RAM, процессов, диска, вывода или времени | Соответствующий лимит срабатывает; хост остаётся работоспособным; причина фиксируется. |
| AC-11 | Отмена команды с дочерним/фоновым процессом | В штатном случае все процессы остановлены не позднее 10 секунд; токены отозваны. При потере управления TTL ограничивает жизнь среды, формируется алерт. |
| AC-12 | Аварийное завершение менеджера и повторный запуск | Просроченные собственные среды обнаружены и очищены, чужие процессы не затронуты. |
| AC-13 | Две задачи и повторная выдача команды | Нет доступа к чужим данным и двойного применения одной операции; конфликт версий виден. |
| AC-14 | Устаревший факт памяти после изменения commit | Факт инвалидирован/перепроверен; источник и причина изменения доступны. |
| AC-15 | Выбранная задача из Kaibain и временный отказ его API | Создаются связанные подзадачи и проекция статуса; после восстановления синхронизация продолжается без дублей. Основная система работает независимо. |
| AC-16 | Чистая установка по README на целевой конфигурации | Проверены готовность, sandbox, доступ к PC и локальная демонстрация без платного API. |
| AC-17 | Запуск evals и имитация ошибок наблюдаемости | Получены воспроизводимые отчёты, связанные traces и работающие алерты; секреты не попадают в экспорт. |
| AC-18 | Приёмка результата пользователем | Принимается именно проверенный хеш/patch; изменения основной ветки после старта выявляются, повторная проверка выполняется при необходимости. |

Для каждого AC сохранить команду/шаги воспроизведения, среду, фактический результат
и артефакты. Успешный негативный тест подтверждает конкретную проверенную границу,
а не отсутствие любых возможных уязвимостей. Нереализованные или неподдерживаемые
проверки нельзя отмечать пройденными.

| 7. Итоговая оценка и сдача | Сравнения и ablation-эксперименты, все приёмочные проверки, семь C4 и Sequence, README, отчёт, демонстрация и перечень ограничений. |

Проверки безопасности, наблюдаемость и измерения сопровождают все этапы. Этап 7
собирает доказательства; он не является первым запуском тестов или мониторинга.
Календарные сроки определяются после уточнения дедлайна и состава участников.
